# v0.2.0 — Capability-first orchestration

> M8 Phase A release-candidate document. The repository operational default switched to capability-first v0.2 before formal publication. This file prepares the `v0.2.0` release contract; a formal release exists only after the Parent-authorized Phase B tag/GitHub Release transaction and independent readback.

## Release summary

`v0.2.0` is the first formal release of the capability-first architecture in which ChatGPT is the authoritative Brain and execution is routed from current runtime capability rather than from a fixed downstream executor.

The four route families are:

- `CHATGPT_NATIVE` — use ChatGPT product/native or connected-app capability when sufficient;
- `CHATGPT_DIRECT_LOCAL` — bounded workspace read/search/status/diff, exact small edits, and focused verification through the Stable Runtime local plane;
- `CODEX_DELEGATE` — sustained local coding, debugging, refactoring, shell-heavy work, and iterative test/build loops;
- `HYBRID` — compose capability planes without making the composition itself a mutation owner.

The operational control loop is:

```text
Evidence first
→ Decision
→ Runtime Capability Discovery
→ Capability Routing
→ Execute
→ Independent Evidence Reacquisition
→ ACCEPT / REVISE / DONE
```

## Major changes since v0.1.0-alpha.3

- Capability-first v0.2 is the repository/default operational contract.
- Native-first routing reuses ChatGPT product capabilities and connected apps instead of routing all work through Codex.
- Secure Tunnel + Local MCP provide the Local Capability Plane only when local-machine/workspace capability is actually needed.
- Direct Local supports bounded workspace operations with canonical-path sensitive-file protections and single-writer mutation ownership.
- Codex App Server is the sustained local coding executor, with durable job/thread/turn bindings and bounded exact recovery instead of most-recent guessing.
- Canonical Governance implements `PLAN / TASK / RESULT / REVISE / REPLAN / ASK_USER / PUBLISH / DONE`, explicit executor/machine/Brain authority separation, and durable Brain Continuity.
- Brain Continuity preserves logical work, Parent fencing, evidence, and bounded semantic recovery across ChatGPT conversation replacement and Local runtime restart.
- Bounded implementation-session continuity permits an authorized non-Parent implementation session to continue the exact current Direct Local step without inheriting Parent control authority.
- Stable Runtime activation supports bounded exact-revision cutover while preserving the stable profile, data root, Governance namespace, and external Secure Tunnel identity.
- Alpha.3/IAB is retained feature-frozen as an **explicit compatibility opt-in only**. Capability/provider failure never silently falls back from v0.2 to Alpha.3.

## Runtime requirements

- Node.js `>=22`.
- Repository CI covers Node `22.x` and `24.x`.
- Git is required for repository/worktree workflows.
- Codex CLI is required only when a task is actually routed to `CODEX_DELEGATE`.

## Upgrade to v0.2.0

1. Use an exact clean checkout of the accepted release commit/tag. Do not infer a release from an operational-default setting alone.
2. Install dependencies from the repository lockfile (`npm ci` is preferred for a clean release checkout; `npm install` remains the documented development quick start).
3. Preserve the existing Stable Runtime configuration, `dataRoot`, Governance namespace, trusted-repository/worktree profile, Codex profile, and external Secure Tunnel identity. Do **not** hand-edit durable Governance JSON.
4. For an already-running Stable Runtime, activate the exact accepted release revision through the bounded activator:

   ```bash
   node scripts/stable-runtime-activate.mjs --sha <exact-40-hex-release-commit> --config <existing-stable-v0.2-config.json> [--repo <trusted-canonical-repo>]
   ```

5. Verify the Stable Runtime health/readiness endpoints report the exact intended revision and that the external tunnel remains ready. Then run the repository verification appropriate to the installation, including `npm test`; `npm run status:brain-command` is the read-only launcher/config check when the user-level launcher is installed.
6. Existing `brain-command` config with no `defaultRuntime` resolves to capability-first `v0.2`. An explicit `defaultRuntime: "alpha3"` remains an intentional legacy compatibility selection. Unknown runtime values fail validation; capability loss does not trigger a silent legacy fallback.

## Durable Governance compatibility and recovery

The canonical v0.2 Governance store uses schema version `1`.

- Known schema `0` state has an explicit deterministic `0 → 1` migration.
- A valid primary state file hydrates normally.
- A corrupt primary with a valid known-good `.bak` recovers from the backup.
- Corrupt primary **and** backup fail closed with a named corruption error.
- A future/unknown schema fails closed with `schema_unsupported`; it is never silently treated as fresh state and is never downgraded through the backup path.
- Atomic persistence commits the new primary first and mirrors that committed snapshot to `.bak`; a corrupt primary is not promoted over the last known-good backup before commit.

Operator rule: if Governance recovery fails closed, preserve the data root and diagnose the exact state/schema condition. Do not bypass the guard with force-unlock behavior, most-recent guessing, or manual durable JSON mutation.

## Stable Runtime rollback boundary

Stable Runtime activation is exact-revision and fail-closed.

- The target must be an exact 40-hex commit reachable from `origin/main` and prepared as an exact clean checkout.
- The existing Stable Runtime endpoint must be healthy/ready immediately before cutover, and the configured external Secure Tunnel lifecycle is preserved.
- A rollback candidate is considered safe only when the currently serving revision is exactly proven by both health/readiness evidence and an exact clean same-profile checkout is available (or a previously validated same-profile activation state matches that serving revision).
- If an exact safe predecessor cannot be proven, activation does **not** guess one. A failed cutover reports no safe rollback rather than starting an unproven revision.

An intentional operational fallback to Alpha.3 is a separate, explicit compatibility choice; it is never the automatic rollback semantics for v0.2 capability/provider failure.

## Publication boundary

Phase A prepares the versioned candidate only. It does **not** create the tag or GitHub Release.

Only after the project-level Parent writes `PARENT_AUTHORIZE_PUBLICATION` may Phase B:

1. merge the accepted RC PR with an exact-head guard;
2. verify post-merge `main` CI;
3. create tag `v0.2.0` at the exact accepted commit;
4. create the matching GitHub Release;
5. read back `main`, tag, and Release and verify version/release-note consistency.

Until that transaction completes, GitHub tag/Release state—not this candidate document—is authoritative for whether `v0.2.0` has been formally published.

## Compatibility boundary

`v0.1.0-alpha.3` remains the historical IAB Direct Brain Loop release. Its implementation is retained under `src/legacy/` as feature-frozen explicit compatibility. v0.2 does not delete it, does not silently route into it, and does not weaken the canonical Governance/recovery model in order to preserve it.
